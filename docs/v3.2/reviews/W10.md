# Wave 10 review

- Date: 2026-11-27
- Scope: 942d7b1 and 1028e9f (detailed git status, upstream gone, cache v2)
- Lenses: correctness, compatibility and performance (one reviewer with
  shell and Docker access, and the 100k-file test repository).

No blocker. Porcelain v2 semantics were checked against `git status`:
renames, `MM`, deletes, intent-to-add, type changes, and the conflicts
`UU`/`UD`/`DU`/`AA`. Hostile filenames cannot forge lines, because git
quotes names that contain a newline. The 2000/2001 boundary, async vs sync,
the mode switch, the old cache and the shell states were checked on bash
4.4 to 5.3.

| ID | Finding | Ruling |
|---|---|---|
| W10-1 (major) | The `+` cap mark went only on the untracked count, so more than 2000 modified files showed `!2000` with no hint | Fixed in 13e260a: `+` goes on the last count shown; test |
| W10-2 | Classic layout in posix mode turned `!` into the history number | Fixed: classic detail segments go through `__bga_ps1_lit`; test |
| W10-3 | A fresh clone of an empty repository showed `gone` (no `branch.ab` before the first commit) | Fixed: an unborn branch (`branch.oid (initial)`) is never gone; test. ADR-0013 wording: compact matches 3.1 except where an upstream really is gone |
| W10-4 | `status.showStash` adds a fifth header, so 2001 entries read as 2000 uncapped | Fixed: the read bound leaves room for five headers; test |
| W10-5 | A newline in a repository's `branch.<name>.merge` can inject fake header and entry lines and skew the counts. ahead/behind/dirty were already affected in 3.1 | Accepted: only numbers reach PS1 (ADR-0008 holds); the effect is a misleading display, from a repository config the trust check already refuses for the worker unless trusted |

Measured (100k files, 5000 modified): compact sync prompt the same as
3.1.0 (0.713 s vs 0.719 s for 10 renders); detail adds about 60 ms per
prompt only with `async = 0`; the worker takes 65 ms in compact and 129 ms
in detail.
